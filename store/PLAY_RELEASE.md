# LandO Google Play release

Package: `com.neotheone.lando` (keep this identifier when creating the listing). Initial version: 1.0.0 / versionCode 1. Support: ftrevino@yahoo.com. The app's display name in its privacy policy is LandO; set your actual developer identity in Play Console.

## Prepared in the project

- Target/compile Android API 36, minimum API 24; no background location, broad storage, camera, microphone or advertising ID permissions.
- An upload-signed release AAB with shrinking enabled. Debug signing is never accepted for a Play bundle. Public upload certificate: `store/upload-certificate.pem`; public fingerprints: `store/upload-certificate-fingerprints.txt`.
- An offline-readable privacy policy and support/licenses page in Settings, cloud/search consent before sending, AI labeling, shared safety instructions, and an in-app answer-report form. Reports include only the selected fields and an answer only with opt-in. A failed/unconfirmed report is not presented as delivered.
- Model downloads are pinned/hash-verified and private; only weights are downloaded, not native executable code. Native runtime libraries ship in the AAB. On-device inference is disabled on 32-bit Android installations that the runtime does not support; mapping/cloud AI remain available.
- Static privacy page `store/privacy-policy.html`, listing copy and release notes, Data safety worksheet, and automated bundle checks. `build/play-store/validation.json` records the actual artifact checks.

## Signing and reproducible build

Privately back up **both** `android/upload-keystore.jks` and `android/key.properties`. They are ignored by Git and have owner-only permissions. The properties file contains passwords: do not put it in a public repo or send it with the app bundle. The public certificate is safe to supply to Google. `tools/create_upload_key.py` refuses to overwrite existing signing files.

Build an internal-testing artifact while Console/service setup is pending:

```sh
python3 tools/build_play_release.py --internal-test
```

After completing the external items below, update `store/release.json` / `store/publishing-status.json` and run without `--internal-test`. The normal command requires the public privacy URL, confirmed reporting delivery, Play-signing Maps restrictions, and reviewed store assets. It runs analyze/tests, builds the signed AAB, verifies the JAR certificate against the saved public certificate, runs Google's pinned/checksummed bundletool, validates API/debug/permissions, and checks 16 KB ZIP configuration plus every 64-bit ELF LOAD alignment. Install Pillow (`python3 -m pip install Pillow` in a virtual environment) to regenerate the deterministic store graphics with `python3 tools/export_store_graphics.py`; no new AI imagery is generated by that script. The supplied screenshots use only a synthetic property on an Android 16 emulator. Review the provenance of the owner-supplied logo for any required listing AI declaration.

Check the artifact at `build/app/outputs/bundle/release/app-release.aab`. The AAB includes R8 mapping and native-symbol metadata.

### Android Studio release builds after integration tests

If Android Studio reports `package dev.flutter.plugins.integration_test does not exist` in `GeneratedPluginRegistrant.java`, regenerate the release plugin registration from the Flutter project root:

```sh
flutter build appbundle --release --dart-define-from-file=store/release.json
```

Then retry the release Gradle task in Android Studio. Integration-test runs can leave generated registration referencing a test-only plugin that is excluded from release dependencies. Do not manually edit the generated Java file or add integration-test code to production. On November 5, 2026, the Flutter release build and direct `:app:bundleRelease` were verified with Android Studio's bundled Java 25 and Gradle 9.3.1. Prefer the release script above for the final artifact so public release configuration and validation are included.

Release APKs now use the upload key by default. Existing debug-signed installations cannot be updated with a differently signed APK/Play installation. Export a LandO backup before migrating those devices. For an APK-only local development update with the old debug certificate, explicitly run `LANDO_DEVELOPMENT_SIGNING=true flutter build apk --release`; this mode is refused for AABs. Never uninstall a data-bearing app just to bypass a certificate mismatch without making a backup.

## External steps before production

1. Publish `store/privacy-policy.html` at a permanent public HTTPS URL. A free static host (for example, a dedicated GitHub Pages repository containing only this policy) is sufficient; no app backend or cloud compute is required. It must load without login or geographic restrictions. Enter that URL in Play Console and optionally `PRIVACY_POLICY_URL` in `store/release.json`. The same full policy is bundled in the app.
2. Activate FormSubmit for ftrevino@yahoo.com and verify a report actually arrives, including a report without an attached answer. The initial setup request encountered HTTP 522 and delivery/activation could not be confirmed. Do not mark reportDeliveryVerified true until tested. If changing the report provider, update the app and policy together. Current endpoint: `https://formsubmit.co/ajax/ftrevino@yahoo.com`. Review submissions and use feedback to improve safety and instructions.
3. Create the app in Play Console, choose Play App Signing, and upload to **Internal testing** first. Let Google manage the app-signing key unless you have a specific signing-key strategy. The local key is the **upload** key, not necessarily the certificate installed on users' phones.
4. In Play Console → App integrity, copy the **APP SIGNING** certificate SHA-1. Add an Android application restriction for `com.neotheone.lando` with that SHA-1 to the Maps/Places key in Google Cloud. Keep debug/upload certificates only where needed for developer/direct APK testing. Restrict the key to Maps SDK for Android and Places API (New). Verify map tiles and an address search from a Play-installed build. No key values are stored in this release packet.
5. Upload the 512×512 app icon, 1024×500 feature graphic and at least two genuine Android screenshots; review `listing-en-US.txt` and `release-notes-en-US.txt`. Keep Google Maps attribution visible. Screenshot examples must not imply real surveyed ownership. Verify/declare AI-generated listing visuals accurately in the Console (the source icon's provenance must be confirmed by the owner).
6. Complete Data safety using `data-safety-draft.md` and current SDK/provider terms; set ads to No, disclose optional AI content generation, complete the content rating, app-access and target-audience questionnaires accurately. The app is intended for adult property planning; do not market it to children. There is no LandO account/login. Explain App access accurately: mapping has no login, and reviewers can use the assistant through Qwen on a compatible 64-bit device after downloading its model, without a cloud account or AI key. Cloud integrations are bring-your-own-key features; do not require a reviewer to purchase a service. If cloud credentials are needed for review, provide a dedicated, controlled review-project key and exact model/setup instructions through the private App access fields, with suitable quotas/budget controls. Do not embed that key in the app, put it in the public listing, or share your personal production key. Keep review access valid throughout the review process.
7. Run Play pre-launch reports, real-device tests (fresh install, denied/approximate location, rotation, Google address search, measurement edits, backups/restore, key storage, online/offline AI, stop/retry, model-download interruption, answer reporting, accessibility and large text). Check for unsafe AI answers and correct failures before production. ELF/ZIP alignment checks do not replace actually running on a 16 KB device/emulator.
8. Complete developer identity/device verification and any testing gate shown for your account. For personal accounts created after November 13, 2023, Google currently requires 12 testers continuously opted into a closed test for at least 14 days before applying for production access. Complete the applicable process; an internal test alone does not satisfy it.
9. Increase the build number for every later upload (for example, `flutter build appbundle --release --build-number=2 --dart-define-from-file=store/release.json`). Review the production rollout manually; nothing here submits or publishes your app.

Google controls final eligibility/review and account-specific requirements. Technical validation is not an approval guarantee.

## Recreate Android screenshots

Use only a temporary emulator with `flutter run -t tools/store_preview.dart -d EMULATOR_ID`. The preview uses an in-memory synthetic property and never opens the real property database. Capture the real map and Layers screens with `adb -s EMULATOR_ID exec-out screencap -p > screenshot.png`. Keep the Google attribution visible in the map view, use the actual app interface, and review image dimensions against current Play requirements. The supplied captures are 1080×1920 PNGs; the feature graphic is 1024×500 RGB PNG and the icon 512×512 32-bit RGBA PNG, under 1 MB.

Android 16 with actual 16 KB pages was tested on November 5, 2026: native map rendering, Qwen download/verification/reuse, offline inference and web research all worked. These are integration checks, not verification of AI-generated facts or contractor pricing.
